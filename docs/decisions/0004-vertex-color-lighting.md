# 光照走顶点色与实例材质乘子，不走引擎光照

## 背景

第一人称几何全用 `Graphics.DrawMesh` 提交，材质是原版 `Map/Cutout`、`Map/Transparent`、地形与植物那几个。这些着色器都不读 `_SceneLight*`，也不接 `Light` 组件：物体永远满亮，正午和半夜没区别。

F013 要让物体受光，必须先定载体。硬约束有两条：

- 本机没有 Unity Editor，自定义 `.shader` 编译不进 AssetBundle，等于没有（`Model3D.cs` 顶部已记同一条）。
- 原版着色器不含 instancing 变体。`Graphics.DrawMeshInstanced` 会**静默**不产生任何像素，`MaterialPropertyBlock` 也没有对应的提交口。

## 决定

- **合批几何的光照写进顶点色 RGB**：地形、墙/岩/门 chunk、实例化的植物/草/物品批、家具与残骸原型网格的形体明暗。载体本身不新增，只是以前没人写。
- **逐件绘制的对象走实例材质乘子**：克隆材质，`color = 原色 × 该处光场亮度`，按量化亮度档缓存。家具、残骸、动物、人物立牌用这一条，因为它们共享原型网格，同一份顶点色不能随位置变。
- **两条通路都只当乘子**：最终颜色 = 贴图 × 材质色 × 顶点色。材质色保留原版染色语义（墙的 `MatAt` 色、植物三档色调），光照一律进顶点色或实例乘子，同一层不两处写。
- **alpha 不是光照通道**。地形顶点的 `colors.a` 是软边遮罩，被 `TerrainFadeRough` 消费；光照只允许写 RGB。

被拒绝的方案：

- `Light` 组件 + 表面着色器：没有 Editor，编不出来。
- Unity lightmap / `uv2`：需要烘焙管线与支持 lightmap 的着色器，同上。
- 后处理或第二台相机叠暗部：拿不到深度，室内室外会互相糊穿；`GodView3D` 那套改 layer 的捕获通路已经够脆，不再加一条。
- 抄原版 `SectionLayer_LightingOverlay` 的黑暗贴片：那是贴地的 2D 网格，在 3D 里盖不住立面，还会和我们的 chunk 抢高度。它的**数值口径**要抄（`glowGrid`、`GroundGlowAt` 的 0.3/0.9 阈值、`GroundGameGlowFactor = 3.6`），绘制方式不抄。

## 后果

顶点色即光照，所以亮度分辨率受网格顶点密度限制。地面那种 16×16 贪心合批的大矩形必须切到 2 m 以内，否则一盏灯在矩形中央只会糊成四角渐变——这是网格层的约束，不是光照层的。

**载体已实机证实，不再靠注释。** 判据是一次单变量实验：设置项 `lightProbe` 把所有烘进网格的顶点色强制成常数灰 (64,64,64)，同机位对照的场景带平均亮度 96.3 → 41.5（2.3 倍），树、草、地面、墙一起变暗。所以 `Map/Cutout`、地形着色器与植物摇摆着色器确实乘顶点色 RGB。此前「手持终端烘了顶点明暗，所以顶点色有效」是拿被检代码的注释当证据，不算证据。

`Map/Transparent` 也被证实吃顶点色 RGB：白天水体按朝向分桶实测北立面 152.9 / 南立面 87.9（同一层内 1.7 倍），只有乘了顶点色才可能出这个差。`Water3D.cs` 里「原版 Transparent 是否读顶点色不确定」的注释就此过期，但那段代码仍按材质色分档走，改不改随下一轮水体工作，别拿旧注释当结论。

同一轮实测还纠正了两个假设：

- 正午看不见明暗不是载体问题，是**合成值超出 1 被截断**：向阳面与天光相加后普遍到 255（`light_check` 的 unlit 计数实测 north 桶 9252 个顶点里 8020 个纯白）。因此合成式加了 `Exposure`（0.62）留出头部空间。
- 原型网格（家具/残骸/动物/植物模型）不能跟着太阳重烘：每过一档清一次全局缓存，实测 7 个植物 OBJ 反复重导入、上百万顶点的实例批反复重建，帧时间直接崩。形体明暗改成固定风格光（与手持终端同一组常数），世界里的方向性由合批几何承担。
- 诊断通道自己也要付帧时间：每 2 s 把所有网格的顶点色与法线整份读出来（foliage 一层 136 万顶点 ≈ 每次几十 MB 临时分配）把 GC 顶到 52~72 MB/s、fps 掉到 7~22。导出改成 6 s 一次并带顶点读取预算，超预算的网格只查「有没有颜色通道」。

**合成式搬进了 `LightShade.cs`，为了让它能在播放器外面被验。** 上面三条都是拿 10 分钟一轮的实机试出来的，太贵，而且实机只能验「有没有差」，验不出「差的量对不对」。现在纯数学（`ILightField` + `LightEnv` + `LightTuning` + 合成函数）单独成文件，`LightField3D` 实现那个接口，`tools/LightSim` 用一座手写 24×24 合成场景（墙 / 厚屋顶房 / 房内红灯笼 / 手工投影块 / 角接触阴影）实现同一个接口 —— csproj 直接 `<Compile Include>` 链接那份公式，不是复制，所以台子过 == 游戏里过。它当场逮到两条实机看不出来的缺陷：

- `Exposure` 0.62 之后正午朝上面仍然被截（模拟台量到 b=1.000，实机对应 terrain 朝上均值 248/255）：截断不是曝光一档能救的，天光项本身按最大通道归一后就能顶到 1.0，与法向直射相加必然越界。改成环境项自带增益 `AmbGain`（0.45，乘在 `AmbientColor` 里，山体那条通路一并吃到）。
- 夜里朝月面与背月面 Δ=0：`MoonStrength` 0.20 乘上曝光只剩 0.124，被 `LightFloor` 0.16 逐通道整个抬起，月光方向被下限吃掉；月色取夜空归一又只剩蓝通道够量级（蓝的亮度权重 0.0722）。改成 `MoonStrength` 0.45 + 偏冷近白月色，并按天空遮蔽门控 —— 厚屋顶下月光与天光一起归零，屋里屋外才不是一个亮法。
